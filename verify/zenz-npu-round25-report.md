# 第25ラウンド: NPU/CPU 偏差の根本原因の切り分け

実施日: 2026-11-22
端末: nubia NX741J（再起動なし）
モデル: v3.2-xsmall Q5_K_M（20.0 MB）、比較用に v3.1 Q6_K / F16

## 1. 結論

**偏差の主因は MUL_MAT の累積誤差で、f16 タイル化ではない。** そして**実機の入力はひらがな**であり、これまでの測定（カタカナ）とは別物だった。

| 問い | 答え |
|---|---|
| f16 タイル化が原因か | **いいえ**（F16 でも同じ偏差） |
| どの演算が主因か | **MUL_MAT**（平均 0.119、他は 0.02 以下） |
| なぜ生成 step 0 で大きく出るか | **KV キャッシュ全体を参照するため** |
| 実機で問題になるか | **ならない**（ひらがな入力では精が優勢） |

## 2. 重要な訂正: 入力形式の違い

**これまでの測定はすべてカタカナ入力（`セイドガタカイ`）でした。実機の IME はひらがな（`せいどがたかい`）を渡します。**

| 入力 | 精 (1246) | 制 (743) | margin | 首位 |
|---|---|---|---|---|
| ひらがな `せいどがたかい` | 16.68 | 16.24 | **+0.44** | 478（別トークン） |
| カタカナ `セイドガタカイ` | 21.31 | 21.70 | **-0.38** | 743（制） |

**ひらがなでは `精` が優勢**なので、実機で `精度が高い` が出るのは正常です。

カタカナで `制度が高い` になるのは、**モデルの想定外の入力**だからです。zenz はひらがなを受け取る前提で学習されています。

**したがって「仲裁 OFF で誤変換が復活する」という私の説明は誤りでした。** 実機では問題ありません。

## 3. 因子分解: 量子化形式 vs 実装差

v3.1 で 2x2 の実験をした（v3.2 の safetensors は非公開のため）。

| モデル | CPU margin | NPU margin | NPU−CPU 差 |
|---|---|---|---|
| v3.1 Q6_K | +1.3718 | +2.2969 | **+0.9251** |
| v3.1 F16 | +1.2197 | +2.2198 | **+0.9999** |

**量子化形式を Q6_K → F16 に変えても、NPU−CPU 差はほぼ変わらない**（0.93 → 1.00）。

| 要因 | 寄与 |
|---|---|
| 量子化形式 | 0.08〜0.15 |
| **NPU vs CPU の実装差** | **0.93〜1.00** |
| 交互作用 | 0.07 |

**実装差が量子化形式の約7倍。** f16 タイル化は主因ではありません。

## 4. 演算別の切り分け

`GGML_HEXAGON_OPFILTER` で演算を1つずつ CPU に落として比較した。HTP バックエンドはフィルタをプロセス起動時に一度だけ読むので、各ケースを別プロセスで実行した。

| フィルタ | 平均変化 | 最大変化 |
|---|---|---|
| **MUL_MAT** | **0.1190** | **0.4586** |
| FLASH_ATTN_EXT | 0.0180 | 0.0686 |
| NORM | 0.0078 | 0.0591 |
| GLU | 0.0000 | 0.0000 |

**MUL_MAT が他を10倍以上上回る。** GLU は GPT-2 では未使用なので変化なし。

## 5. 中間テンソルの比較

`cb_eval` フックで最終 norm と logits を NPU/CPU 両方でダンプした。

### step 別の norm 差

| step | mean_abs_diff | max_abs_diff |
|---|---|---|
| -1（プロンプト） | 0.147 | 0.832 |
| **0（最初の生成）** | **1.261** | **4.746** |
| 1 | 0.632 | 2.415 |
| 2 | 0.332 | 1.616 |
| 3 | 0.346 | 2.176 |
| 4 | 0.214 | 0.968 |

**step 0 だけが突出**し、その後は 0.2〜0.6 に収束する。

### 解釈

- プロンプト処理で K/V を計算 → 差が蓄積（0.147）
- 最初の生成で全 K/V を参照 → 差が増幅（1.261）
- 以降は新しい K/V のみ追加 → 差が縮小

**KV キャッシュに差があり、それを最初の生成で全体参照するため step 0 で最大になる。**

### logits への影響

```
result_output|0: max_abs_diff = 12.33
tok=1246 精: npu=-5.4167 cpu=-0.0499 delta=-5.3668
tok=743  制: npu= 4.9758 cpu= 0.0829 delta=+4.8929
```

## 6. 根本原因のまとめ

**単一のバグではなく、MUL_MAT の数値差が層を重ねて蓄積した結果。**

1. HTP の MUL_MAT は CPU と積和の順序・タイル分割が違う
2. その差が層ごとに蓄積する
3. プロンプト処理で KV キャッシュに差が入る
4. 最初の生成で全 KV を参照するため差が最大になる
5. 以降は新規トークン分だけなので薄まる

**f16 タイル化、GELU 近似、softmax 近似はいずれも主因ではない**（フィルタ実験で寄与が小さいことを確認）。

## 7. 実用上の結論

**仲裁 OFF で運用する。** 実測速度:

| 読み | 仲裁 ON | 仲裁 OFF |
|---|---|---|
| セイドガタカイ | 568-636 ms | **14-19 ms** |
| カンジヘンカン | 21-25 ms | **12-17 ms** |
| ニホンニュウリョク | 24-25 ms | **15-17 ms** |
| キョウハテンキ | 27-35 ms | **16-19 ms** |

中央値 **16.6 ms**（仲裁 ON は 27ms）。

**実機のひらがな入力では `精` が +0.44 優勢**なので、仲裁なしでも正しい変換になります。
