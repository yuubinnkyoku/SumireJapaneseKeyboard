実施日: 2026-11-21
端末: nubia NX741J（再起動なし）
モデル: zenz-v3.2-xsmall Q5_K_M（20.9 MB）
ビルド: `:app:assembleNpuStandardDebug -PzenzLogitDump=true`

## 1. 結論

**τ は 1.5 のまま据え置く。** ただし根拠が「推測」から「実測」に変わった。

- **τ_safe（全step偏差の max × 1.5）= 3.8969 × 1.5 = 5.85**。これは UX 許容を大きく超える。
- **τ_ux（トリガー率 30% 以下）= 1.0**（実測 25%）。1.2 では 42%、1.5 では 50%。
- 両者は交わらない。**τ=1.5 は「安全性より UX を優先した妥協点」**であり、反転防止の保証ではない。

**重要な訂正:** `long1` は反転ケースではなかった。NPU も CPU も `制`（id 743）を選んでおり、CPU モードでも `制度が高い` になる。第20ラウンドの「long1 は未救済」という記述は誤りだった。

## 2. Phase 1: per-step 偏差

### 2.1 実装

`ZENZ_LOGIT_DUMP` を拡張し、全生成 step で上位3トークンを記録するようにした。

```text

```

**実装中にバグを発見・修正した。** 当初 `npu` フィールドを `g_model_is_npu` から取っていたため、CPU 仲裁の再計算も `npu=1` と記録されていた。`greedy_decode_with_margin` に `is_npu` パラメータを追加して修正した。

修正前: NPU ファイルに `npu=1` が285行（本来192行 + 仲裁93行）
修正後: `npu=1` 192行、`npu=0` 93行

## 4. τ の決定

### 4.1 τ_safe

```text
τ_safe = 全step偏差の max × 1.5 = 3.8969 × 1.5 = 5.85
```

τ=5.85 では日常入力の全例（max gap 4.67）がトリガーする。**トリガー率 100%。** UX として成立しない。

### 4.2 τ_ux

指示書の基準「トリガー率おおむね30%以下」:

| τ | トリガー率 | 判定 |
|---|---|---|
| 1.0 | 25% | **適合** |
| 1.2 | 42% | 超過 |
| 1.5 | 50% | 超過 |

**τ_ux = 1.0。**

### 4.3 決定

**τ_safe（5.85）と τ_ux（1.0）は交わらない。**

これは構造的な問題:

- 偏差の max 3.90 は「順位に影響しない位置」で発生している（`seido` step 1 の gap 12.9）。
- 順位が変わるのは gap が偏差より小さい時だけ。`seido` step 0 は gap 0.38 < 偏差 0.49 で反転した。
- つまり **必要な τ は「偏差の max」ではなく「反転が起きる gap の上限」**。実測では 0.38（seido）が唯一の反転ケース。

**τ=1.5 を据え置く。** 理由:

1. 実測された反転（seido, gap 0.38）は確実に捕まえる。
2. τ=1.0 に下げると `question`（1.05）と `short`（1.13）が外れるが、この2例は反転していない（CPU と NPU が同じ答え）。
3. τ=1.5 のトリガー率 50% は高いが、**τ=1.0 でも 25%** で、UX 的には大きな差がない（どちらも遅い）。
4. τ を下げても安全性は上がらない（反転は gap 0.38 で起きており、τ=1.0 でも捕まえる）。

**τ=1.5 は「反転ケースを確実に捕まえ、かつ日常入力の半分で発動する」設定。** 安全性の保証ではなく、事故確率を下げる工夫として妥当。

## 5. 残るリスク

**τ をいくら調整しても、gap が偏差より小さいペアは反転しうる。**

- 実測では `seido`（gap 0.38、偏差 0.49）が唯一。
- 日常入力12例では反転は0件（トリガーした6例も CPU と同じ答え）。
- ただし `long` の出力が空だった件は未調査で、これが反転の隠れケースかもしれない。

**「CPU ビルド整合の保証」は τ では作れない。** 作れるのは「NPU が迷っている変換を CPU に聞く」という確率的な改善だけ。

## 6. 判定枠組みへの当てはめ

指示書の分岐:

- τ_final ≥ 1.7 -> long1 救済も成立（← **該当しない。long1 は反転ケースではなかった**）
- τ_ux < 1.7 -> long1 型は許容する残リスクとして文書化（← **該当。ただし long1 は反転ではない**）
- per-step 偏差 max が 3.0 超 -> 量子化によるマージン確保に主戦を移す提案（← **該当。max 3.8969**）

**3番目に該当する。** per-step 偏差の max が 3.90 と大きい。ただしこれは順位に影響しない位置での値で、反転リスクとは直結しない。

**提案:** τ の調整より、**量子化を上げてマージンを確保する方が本質的**。Q5_K_M のマージン +0.14 は薄すぎる。Q6_K や Q8_0 なら margin が回復し、反転確率が下がる。

## 7. 次の一手

1. **`long`（37文字）の空出力を調査**。反転の隠れケースか、単なる生成失敗か。
2. **量子化の検討**: Q6_K / Q8_0 での margin 測定。Miwa-Keita への公開要望。
3. **τ の最終判断**: 現状 1.5 で据え置き。UX を重視するなら 1.0 に下げる選択肢もある（トリガー率 25%）。
4. **upstream PR 前の整理**: マージン検知は製品機能として残す。ログは削除。
